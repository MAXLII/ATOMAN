# FAL 分层工程方案

## 1. 方案定位

本方案定义 Flash 存储能力从底层驱动到应用使用的装配方式，适用于具有单颗或多颗 Flash 的嵌入式项目。分层依据是职责与依赖，具体芯片、总线、容量、分区用途和应用数据格式由目标工程确定。

FAL 系统由 BSP、Interface、fal_cfg、fal_core 和应用使用层组成。Demo 是应用使用层的一种实现。这里的 FAL 系统指存储子系统；工程中的 SECTION 和 DBG 仍承担注册调度与观测职责。

本文件是工程方案，不作为具体目标已完成接入、构建或硬件验证的证明。Core 的详细数据结构和状态机见 [FAL Core 设计](fal_design.md)，操作接口见 [FAL 使用说明](../../application/storage/fal_usage.md)。

## 2. 总体关系

### 2.1 搭建顺序

```text
BSP → Interface → fal_cfg → fal_core → 应用使用层（Demo）
硬件能力   项目接口      配置装配      运行管理       实际用途
```

该顺序表示先提供能力，再完成装配，最后交给应用使用。它与运行时的函数调用方向不同。

### 2.2 运行关系

```text
fal_cfg ──设备参数、分区表、操作表与实例绑定──→ fal_core

应用使用层 ──分区请求──→ fal_core
                           │ 已挂载的操作回调
                           ↓
                    Interface → BSP → Flash
```

操作回调直接匹配 Interface 函数时，由配置挂载该函数；需要类型、状态或设备上下文转换时，由 fal_cfg 中的薄适配函数转接。fal_cfg 的角色是装配，Core 运行时消费其配置与回调。

## 3. 五层职责

| 层级 | 核心职责 | 对外提供 |
|---|---|---|
| BSP | 实现目标 Flash 的物理访问与芯片约束 | 初始化、读、编程、擦除、状态与物理能力查询 |
| Interface | 将 BSP 能力整理成项目统一接口 | 独立于 FAL 类型的普通函数和接口契约 |
| fal_cfg | 将项目接口装配为可用的 FAL 配置 | 操作表、设备参数、分区表、上下文和实例绑定 |
| fal_core | 管理请求的校验、执行和状态推进 | 分区访问、请求状态、完成结果和调度入口 |
| 应用使用层 | 实现数据存储的实际用途 | 参数保存与加载、日志、存储测试等功能 |

### 3.1 BSP：物理驱动

BSP 负责总线事务、芯片命令、物理地址访问、芯片忙状态与错误报告。芯片要求的页边界、擦除粒度、编程顺序及 ECC、坏块检测等介质约束，由相应驱动处理。

BSP 对整个目标器件提供基础访问能力，检查物理边界与驱动参数。项目分区和区域访问权限由 fal_cfg 描述、fal_core 执行。

### 3.2 Interface：项目统一接口

Interface 提供与 `fal_flash_ops_t` 所需能力对应的函数实现，内部通过 BSP 完成访问。它使用自身的设备标识、参数、状态和返回值定义。

**Interface 不包含 FAL 头文件，不使用 `fal_flash_ops_t` 或其他 FAL 类型，不创建 FAL 操作表。** “提供 FAL 所需函数”描述的是能力匹配，而不是类型依赖。

接口契约覆盖初始化、状态查询、读取、编程和擦除；几何参数查询、同步与健康信息按实际能力提供。跨平台实现保持相同的 API 命名、参数语义、单位、错误含义和时序约定。

### 3.3 fal_cfg：项目配置与装配

fal_cfg 同时了解 Interface 公共接口和 FAL 公共类型，承担以下配置职责：

- 将 Interface 函数挂载到 `fal_flash_ops_t`。
- 在必要时转换设备上下文、返回值和状态，保持函数指针签名一致。
- 描述容量、编程页、最小编程单位、擦除块和单次传输约束。
- 定义分区标识、布局、容量和读写擦权限。
- 绑定设备配置、操作上下文及 FAL 实例。

fal_cfg 属于项目装配配置。在 Demo 工程中由 Demo 提供一份配置；具体设备数量与分区用途随项目确定。配置对象和回调上下文的生命周期覆盖对应实例的使用周期。

通用初始化流程、请求推进和多实例调度机制归 Core；工程启动与周期入口负责调用这些机制。

### 3.4 fal_core：lib 中的通用运行管理

fal_core 归属 `lib` 通用库，统一放在 `code/lib/fal/` 下，由各项目复用。它以硬件无关的分区与请求管理能力服务应用侧存储功能。

Core 通过传入的配置与操作表访问设备，负责：

- 校验设备参数、分区布局及必需操作能力。
- 检查分区、偏移、长度、权限与对齐要求。
- 将分区地址换算为目标设备地址，并按设备约束拆分请求。
- 执行读、写、擦状态机，查询设备状态并记录完成或错误结果。
- 管理实例的初始化与运行状态，按明确的串行化规则推进请求。

Core 依赖 FAL 公共契约，不包含具体项目的 fal_cfg、Interface 或 BSP 头文件。它通过配置注入获得设备能力；项目数据的含义、记录格式和保存策略由应用侧定义。

### 3.5 应用使用层：实际用途

应用使用层通过逻辑分区与分区内偏移发起存储操作，处理请求提交结果和最终完成结果。Demo 展示这些操作如何组合成可使用的功能。

参数版本、校验、双副本切换、日志组织和恢复策略归应用侧存储服务。Flash 擦写完成与应用记录有效是两个判断层次，由各自负责的模块报告结果。

## 4. 接口与运行契约

### 4.1 地址和数据单位

Interface 明确设备地址空间、地址单位、长度单位和缓冲区表示方式；fal_cfg 转换为 Core 使用的统一语义。含主区与附加区的介质明确各自寻址边界。

涉及不同 C 字节宽度的平台时，明确物理 8 位存储单元与 C 对象的表示和转换，不能通过 `sizeof` 或指针类型默认为两者等价。

### 4.2 请求与完成

提交成功表示请求已被接受；操作是否完成由运行状态和最终结果确定。异步期间，调用方保持缓冲区有效，并遵守读写所有权约定。

驱动报告的忙、就绪和错误状态，经 Interface 和配置适配传递给 Core。状态转换保持真实含义，错误不能转换为成功。超时检测与恢复由接入契约明确执行者及时间基准。

### 4.3 调度和并发

工程启动入口按依赖顺序初始化 FAL 和应用存储服务；周期入口调用 Core 推进函数，应用侧在观察到完成后推进自身流程。

同一实例的请求提交、状态推进和重新初始化采用一致的串行化规则。多个实例访问同一物理设备时，还需统一设备级互斥与总线所有权；实例数量本身不代表硬件可以并行访问。

### 4.4 配置与安全边界

分区范围位于设备容量内，布局满足擦除对齐与权限要求。Core 在执行前检查这些限制，BSP 独立维护芯片物理限制。

项目对划分后的区域指定读、编程和擦除权限；分区权限约束经过 FAL 的访问路径。上电初始化和配置绑定不等同于授权擦除或格式化。

## 5. 工程组织与接入

Interface 按项目组织，公共声明和可共用实现归 `code/interface/<project>/common/`，不能共用的实现归同项目下的真实平台名称目录。每个目标选择一套项目 Interface 与相应 BSP。

fal_cfg 与该项目的存储使用配置一起维护；Core 源码与公共头文件统一归入 `code/lib/fal/`。项目记录格式、参数恢复和数据池联动由应用侧存储服务负责。构建目标显式选择配置源文件、Interface 实现和 BSP 驱动，避免同一能力的多套实现重复链接。

接入按以下步骤完成：

1. 确认 BSP 能正确访问目标 Flash，并描述其真实物理约束。
2. 提供项目 Interface，确定参数、单位、状态和缓冲区契约。
3. 在 fal_cfg 完成操作挂载、设备描述、分区及实例绑定。
4. 在启动和周期入口接入 Core 的初始化与状态推进。
5. 由应用侧提交请求并处理结果，实现具体存储用途。

数据池联动由应用侧存储服务完成：业务通过 business 接口访问数据池，存储服务通过 exchange 接口获取待保存快照或发布恢复结果。数据池保持纯内存职责；Core 处理分区数据，不解释数据池字段。

## 6. 验证要求

- 依赖检查：BSP、Interface 无 FAL 类型耦合；Core 通过配置和回调获取设备能力。
- 配置检查：容量、对齐、分区权限、设备映射和回调完整性满足约束。
- 状态检查：覆盖提交、忙、完成、错误及再次请求，验证缓冲区生命周期。
- 隔离检查：无效请求和越界请求不触发实际擦写；共享设备的实例访问受控。
- 应用检查：按记录策略验证保存、加载、校验失败和中断恢复。

主机模拟可验证软件逻辑，目标构建验证工程集成，实物读写验证总线和器件行为。三者分别记录结果。

## 7. 示例：双 Flash Demo 接入

以下示例说明前述方案的落地方式，设备数量、分区名称与容量属于示例配置。

### 7.1 文件与职责映射

下表对应本工程的接入目录，Core 源码和公共头文件位于 `code/lib/fal/`。

| 层级 | 示例组织位置 | 内容 |
|---|---|---|
| BSP | `platform/gd32e507/bsp/` | NOR、NAND 访问及设备分发 |
| Interface | `code/interface/demo/common/flash_port.c/.h` | 普通 Flash 操作函数与独立接口类型 |
| fal_cfg | `code/business/demo/fal_cfg.c/.h` | 操作回调适配、设备表、分区表和实例绑定 |
| fal_core | `code/lib/fal/fal_core.c/.h` | lib 中的通用 FAL 运行管理 |
| Demo | `code/business/demo/demo_fal.c`、`code/data_source/demo/` | 操作入口、参数与日志存储服务 |

### 7.2 配置内容

Demo 为一颗 NOR 和一颗 NAND 分别挂载 Interface 操作，并描述各自的容量、页与擦除块参数。每颗设备划分保护区、参数 A、参数 B、测试区和日志区，权限与容量在 fal_cfg 中配置。

读回调由配置适配函数接收 FAL 上下文，定位 Interface 设备标识，调用 `flash_port_read`，再将接口返回值转换为 FAL 结果。编程、擦除和状态查询采用相同的装配关系。

### 7.3 一次参数保存

1. Demo 提交保存命令，存储服务通过数据池 exchange 接口取得待保存快照。
2. 存储服务构造记录，并按保存策略向目标参数分区提交擦除和写入请求。
3. Core 校验请求，通过配置回调调用 Interface，再由 BSP 操作 Flash。
4. 周期入口推进 Core；存储服务根据最终结果继续校验、提交记录或报告失败。
5. 存储服务经 exchange 接口发布结果，业务经 business 接口读取状态。

具体分区与操作方式见 [GD32E507 双 Flash Demo](../../application/storage/gd32e507_fal_demo.md)。
