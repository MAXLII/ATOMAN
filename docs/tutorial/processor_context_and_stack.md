# 处理器现场、栈与上下文切换基础

## 1. 执行现场是什么

处理器执行程序时，当前位置不仅由程序计数器决定。要让一段被暂停的代码从原位置继续，必须恢复完整执行现场。

典型执行现场包括：

- 程序计数器或返回地址。
- 栈指针。
- 通用寄存器。
- 处理器状态寄存器。
- 浮点和向量寄存器。
- 调用栈中的局部变量、参数和返回链。

上下文切换的本质是保存任务A的现场，选择任务B，再恢复任务B的现场。

```mermaid
flowchart LR
    A[任务A运行] --> SA[保存A寄存器和栈位置]
    SA --> S[调度器选择任务B]
    S --> RB[恢复B栈位置和寄存器]
    RB --> B[任务B从原位置继续]
```

## 2. 寄存器和程序状态

处理器通常包含：

- 通用寄存器：整数计算、地址和临时数据。
- SP：当前栈顶位置。
- LR：函数或异常返回位置。
- PC：下一条执行指令位置。
- 状态寄存器：条件标志、中断屏蔽、处理器模式等。
- 浮点/向量寄存器：浮点和SIMD计算状态。

只保存PC而不保存其他寄存器，恢复后计算中间值会改变；只保存寄存器而不保存栈，局部变量和返回地址会丢失。

## 3. 函数调用栈

函数调用通常包含：

1. 调用者准备参数。
2. 保存需要跨调用保留的值。
3. 记录返回地址。
4. 被调用者为局部变量分配栈帧。
5. 函数返回时按相反顺序恢复。

```text
高地址
┌──────────────────┐
│ 上层函数栈帧     │
├──────────────────┤
│ 返回地址/保存寄存器│
├──────────────────┤
│ 当前函数局部变量 │ ← 当前SP附近
└──────────────────┘
低地址
```

栈帧内容由编译器、优化级别、ABI和函数代码共同决定。C语言不能假设某个局部变量总位于固定偏移。

## 4. ABI与调用约定

ABI定义不同编译单元和不同语言之间如何协作，包括：

- 参数放在哪些寄存器或栈位置。
- 返回值如何传递。
- 哪些寄存器由调用者保存。
- 哪些寄存器由被调用者保存。
- 栈必须按多少字节对齐。
- 浮点参数使用哪组寄存器。
- 结构体参数和返回值如何处理。

上下文切换汇编必须遵守ABI。如果遗漏被调用者应保留寄存器，任务恢复后可能在远离切换点的位置才暴露错误。

### 4.1 调用者保存与被调用者保存

调用者保存寄存器允许被调用函数自由覆盖，需要时由调用者在调用前保存。被调用者保存寄存器必须在函数返回前恢复原值。

任务切换不同于普通函数调用。任务可能在任意允许抢占的位置暂停，因此切换入口需要保存足以恢复整个任务的寄存器集合，而不能只依赖某一方的普通函数责任。

## 5. 硬件现场与软件现场

进入异常时，一些处理器会自动把部分寄存器压栈，这称为硬件现场。未自动保存的寄存器由异常入口软件保存。

```text
异常进入
  ├─ 硬件保存最小返回现场
  ├─ 软件保存剩余寄存器
  ├─ 调度器选择目标任务
  ├─ 软件恢复目标寄存器
  └─ 异常返回恢复硬件现场
```

另一些处理器需要异常入口显式保存更多状态。无论具体机制如何，保存布局和恢复布局必须完全对称。

## 6. 首次任务启动

新任务没有“以前保存的现场”。内核需要人工构造一个看起来像被切出过的初始现场：

- 初始PC指向任务入口。
- 返回地址指向任务退出处理函数。
- 状态寄存器设置为正确模式和指令集状态。
- 栈指针对齐到ABI要求。
- 参数寄存器保存任务入口参数。

调度器第一次恢复该现场时，处理器会像异常返回一样进入任务入口。

任务函数意外返回时，不能跳到未知地址。初始返回地址必须指向受控的任务完成或故障处理入口。

## 7. 每任务独立栈

传统RTOS通常为每个任务分配独立栈：

```text
任务A：TCB + Stack A
任务B：TCB + Stack B
任务C：TCB + Stack C
```

切换时保存当前SP，再加载目标任务SP。局部变量和调用链一直留在各自栈中，不需要复制。

内存预算近似为：

$$
M_{stack}=\sum_{i=1}^{n}S_i
$$

其中 $S_i$ 是任务 $i$ 为最坏调用深度预留的栈容量。

优点：

- 任意Ready任务可以直接恢复。
- 切换时间与已用栈深度基本无关。
- 调试器容易分别查看各任务栈。

代价：

- 每个任务永久占用最坏栈预算。
- 栈估算过大会浪费RAM，过小会溢出。
- 任务数量增加时总栈线性增长。

## 8. 公共运行栈与现场快照

另一种方法让任务在同一块公共运行栈上运行。任务暂停时，把从当前SP到栈顶之间实际使用的内容保存到快照区；恢复时再复制回来。

```mermaid
flowchart LR
    RUN[任务在公共栈运行] --> SAVE[复制实际已用栈片段]
    SAVE --> SNAP[任务快照]
    SNAP --> RESTORE[复制回公共栈]
    RESTORE --> RUN2[从原调用位置继续]
```

内存预算近似为：

$$
M_{stack}=S_{runtime,peak}+\sum S_{suspended,actual}
$$

优点：

- 不为每个任务永久保留完整最坏栈。
- 同时悬挂任务较少时可能节省RAM。

代价：

- 切换需要复制内存。
- 切换时间随实际栈深度变化。
- 快照区容量由同时悬挂现场共同决定。
- 快照分配、恢复和回收必须保持一致。

两种模型是时间与空间的交换，没有绝对优劣。

## 9. 快照池与环形分配

多个暂停任务的快照可以放入固定容量内存池。FIFO恢复顺序允许使用环形分配：

```text
head：最早待释放快照
tail：下一次分配位置
used：当前已占用容量
```

环形池必须维护以下不变量：

- `used` 不超过总容量。
- head和tail始终在合法范围。
- 每个快照的地址和长度都在池内。
- 释放顺序与分配顺序一致。
- 环尾绕回产生的空洞被正确计入或跨越。

如果调度器需要任意顺序恢复任务，FIFO环形池可能不再适用，需要固定块、伙伴系统或其他可独立释放方法。

## 10. 栈对齐

ABI通常要求栈在函数调用或异常边界保持特定对齐，例如8字节或16字节。

未对齐可能导致：

- 多字加载指令异常。
- 浮点和向量访问失败或变慢。
- 被调用库函数违反ABI假设。
- 异常返回无法识别现场。

栈顶地址和每次保存的现场大小都要维持对齐。人工构造初始帧时尤其容易出错。

## 11. 浮点现场

使用FPU后，任务现场可能显著增大。必须回答：

- 所有任务都保存完整浮点现场，还是只保存使用FPU的任务？
- 处理器是否支持lazy stacking？
- 异常嵌套时浮点现场位于哪里？
- 编译器使用hard-float还是soft-float ABI？

lazy stacking推迟浮点压栈，可以降低不使用FPU时的异常开销，但使现场大小和保存时机更复杂。追求确定性时，系统可能选择关闭lazy机制或显式记录扩展帧是否存在。

C文件、汇编端口和链接库必须使用一致浮点ABI。

## 12. M-profile异常模型基础

典型M-profile处理器区分：

- Thread模式：运行普通代码。
- Handler模式：运行异常和中断。
- MSP：常用于异常和启动代码。
- PSP：可用于任务栈。

常见任务切换结构：

- SVC用于从普通代码请求受控内核服务或启动首个任务。
- PendSV配置为最低优先级，用于延迟上下文切换。
- 硬件异常帧保存基本返回现场。
- PendSV软件保存剩余寄存器并交换PSP。

最低优先级PendSV确保外设中断先完成，再在安全的异常返回路径切换后台任务。

## 13. A-profile异常模型基础

典型A-profile处理器具有多种运行模式，并为部分模式提供banked寄存器或独立栈指针。

相关概念包括：

- System/User模式运行任务。
- SVC模式执行系统调用或调度器。
- IRQ模式响应普通中断。
- CPSR保存当前处理器状态。
- SPSR保存异常前状态。
- VBAR指定异常向量表基址。
- 异常返回同时恢复PC和处理器状态。

如果调度器使用独立SVC栈，复制公共任务栈时不会覆盖调度器自己的调用帧。IRQ栈、SVC栈和任务栈的边界必须分别规划。

## 14. 中断返回与任务切换

中断唤醒任务后，不应在任意C函数中直接替换SP。典型方法是在统一中断返回路径处理：

```text
进入IRQ
  → 保存IRQ所需现场
  → 执行设备中断处理
  → 判断是否需要调度
  → 必要时保存被中断任务完整现场
  → 恢复目标任务现场
  → 异常返回
```

发布“需要切换”与真正执行切换是两个阶段。这样设备ISR只产生调度请求，低层异常端口负责安全交换现场。

## 15. C与汇编的边界

汇编适合处理：

- 读写栈指针和状态寄存器。
- 批量保存寄存器。
- 异常进入和返回指令。
- 处理器模式切换。

C适合处理：

- Ready队列和等待队列。
- 任务状态。
- 时间管理。
- 调度策略和故障记录。

边界接口应尽量小，例如“传入当前SP，返回目标SP”。汇编不理解任务策略，C代码不假设寄存器帧之外的异常细节。

## 16. 栈容量与高水位

栈容量必须覆盖：

- 最大函数调用深度。
- 最大局部变量占用。
- 编译器保存寄存器。
- 中断嵌套或异常帧。
- 浮点扩展现场。
- 库函数的内部栈使用。

常用高水位方法是在启动时用固定图案填充栈，运行后扫描仍未被覆盖的区域。

高水位表示测试中观察到的最大使用量，不等于理论最坏值。最终容量还应保留中断嵌套、未覆盖路径和版本变化裕量。

## 17. 现场完整性与故障

上下文错误常见来源：

- SP越过栈边界。
- 保存和恢复寄存器集合不对称。
- 浮点帧判断错误。
- 栈对齐错误。
- 快照长度或地址损坏。
- 异常返回状态不合法。
- C与汇编ABI不一致。

恢复损坏现场可能跳转到任意地址。可靠系统应在恢复前检查地址、长度、对齐和状态，在无法证明现场有效时停止恢复并保留故障证据。

## 18. 调试方法

建议记录：

- 当前任务名称。
- 当前SP和栈边界。
- 保存PC和处理器状态。
- 栈最小剩余空间。
- 快照池当前值和高水位。
- 保存、恢复和释放计数。
- 最近一次故障原因。

调试器中应分别确认：

1. 新任务初始PC正确。
2. 切出前后局部变量保持一致。
3. 整数任务和浮点任务互不污染。
4. 中断栈与任务栈没有重叠。
5. 优化构建与调试构建都遵守同一ABI。

## 19. 实验和思考题

建议实验：

1. 编写多层函数调用，观察SP和栈帧变化。
2. 比较不同优化等级下的栈使用量。
3. 人工构造一个任务初始帧，并让它进入指定入口。
4. 在两个任务间反复切换，校验通用寄存器和局部变量。
5. 加入浮点计算，比较保存现场大小变化。
6. 缩小栈容量，验证高水位和越界检测。

思考题：

1. 为什么普通函数调用约定不足以自动完成任务切换？
2. 每任务独立栈和快照模型分别把成本放在什么地方？
3. 为什么调度器自身不应在正在被复制的任务栈上运行？
4. lazy stacking为什么会让现场大小判断复杂化？
5. 为什么恢复现场前的边界检查比恢复后的故障捕获更重要？
