# GCC Host Testbench Usage

## 1. Purpose

The host testbench validates pure-software DUTs with GCC without starting an MCU, MATLAB, or PLECS project. DUT means Design Under Test and refers to the object being tested. A DUT may be a function, reusable module, algorithm, or complete software subsystem.

This document is also the implementation contract for AI-assisted test creation. Before adding or changing a host test, inspect the current files under `platform/testbench/` and follow the lifecycle and build rules below.

The testbench provides:

- static registration of multiple DUT modules;
- static registration of multiple cases under each DUT module;
- one executable that discovers and runs every linked module and case;
- deterministic simulated time based on each DUT module's run period;
- mixed C and C++ DUT support through a C++ common runner;
- process exit status suitable for automated scripts;
- CSV waveform or Bode data generated by individual test cases.

## 2. Current Directory Layout

```text
platform/testbench/
├── common/
│   ├── testbench.h
│   └── testbench.cpp
├── ac_loss_det/
│   ├── Makefile
│   ├── ac_loss_det_test.c
│   └── ac_loss_det_test.h
└── pi/
    ├── Makefile
    ├── pi_test.c
    └── pi_test.h
```

Create each new test project as a sibling of `common/`. Keep the production DUT in its original repository location and compile that source directly. Do not copy or move a production `.c` or `.h` file into the test directory.

Use a test header for fixture types, scenario enums, and shared declarations. A fixture is the test context that owns the DUT instance, inputs, outputs, simulated environment state, recording resources, and case-local result state. Use a test source for fixtures, callbacks, assertions, CSV output, and registration. Every new project-owned `.c` and `.h` file must use the repository file header template.

Generated files belong under the test project's `build/` directory. The repository ignores these build directories.

## 3. Required Host Tools

Verify the MinGW toolchain:

```powershell
gcc --version
g++ --version
mingw32-make --version
```

The supplied Makefiles use:

- GCC for C sources;
- G++ with C++14 support for the common runner and C++ sources;
- GNU ld automatic `__start_<section>` and `__stop_<section>` symbols;
- `mingw32-make` available on `PATH`;
- PowerShell for removing compiler outputs before each build.

The supplied `testbench.cpp` is implemented in C++ so the same executable can contain either C or C++ DUTs. Compile each DUT, dependency, and test support source with the compiler and language standard appropriate to that source. The reference Makefiles compile the runner as C++14 and use G++ for the final link because the runner uses the C++ standard library. Another build system may use an equivalent C++ compiler and linker configuration.

## 4. Registration API

Include the common interface by filename:

```c
/* Import the registration macros and test case state definitions. */
#include "testbench.h"
```

Register one DUT module with:

```c
/* Register one DUT and define the interval between adjacent executions. */
TESTBENCH_REGISTER(test_name, period_s, dut_init, dut_run)
```

Parameters:

| Parameter | Meaning |
|---|---|
| `test_name` | A valid identifier suitable for macro token concatenation; it is used as the display name, descriptor symbol suffix, and case-section suffix. |
| `period_s` | The positive interval between DUT executions, in seconds. For example, `0.001` is 1 ms. |
| `dut_init` | DUT initialization called once before every individual test case. |
| `dut_run` | The DUT body called once on every simulated execution beat. |

Register each case independently with:

```c
/* Register one independently initialized scenario under the DUT module. */
TESTBENCH_CASE(test_name, case_name, init, before_dut, after_dut)
```

Parameters:

| Parameter | Meaning |
|---|---|
| `test_name` | Must exactly match the owning `TESTBENCH_REGISTER` name. |
| `case_name` | A valid identifier suitable for macro token concatenation; it is used as the case name and descriptor symbol suffix. |
| `init` | Initializes the isolated case environment, fixture, scenario, and recording resources. |
| `before_dut` | Advances and prepares the environment before the current DUT execution. |
| `after_dut` | Observes the current DUT output, applies immediate effects, records results, and returns the case state. |

Both macros expand to file-scope structure declarations. Their macro definitions own the terminating semicolon. Therefore, invocations do not have a semicolon:

```c
/* Register the DUT module once. */
TESTBENCH_REGISTER(example, EXAMPLE_PERIOD_S, dut_init, dut_run)

/* Register one test case belonging to the example DUT module. */
TESTBENCH_CASE(example,
               nominal_response,
               nominal_init,
               nominal_before_dut,
               nominal_after_dut)
```

The current registration macros use C designated initializers, so the reference layout keeps the small source file that expands `TESTBENCH_REGISTER` and `TESTBENCH_CASE` in C11. This does not restrict the DUT itself to C: C++ DUT and support sources can be compiled separately with G++ and linked into the same executable.

## 5. Runtime Lifecycle

The executable constructs linked lists from GCC sections and runs every registered case. For each case, the common runner executes:

```text
case init
DUT init

beat 1:
    before_dut(Ts)
    dut_run()
    after_dut(Ts)

beat 2:
    before_dut(2 * Ts)
    dut_run()
    after_dut(2 * Ts)

...
```

Beat 0 is reserved for initialized conditions. Case initialization runs before DUT initialization, so a case can open its CSV in `init` and record the initialized DUT state at the end of `dut_init`:

```c
static void dut_init(void)
{
    production_module_init(&fixture.dut, &fixture.input, &fixture.output);
    process_record(0.0); /* Capture the initialized DUT state as beat 0. */
}
```

`after_dut()` ends a test case by returning `TESTBENCH_CASE_COMPLETE`, `TESTBENCH_CASE_PASS`, or `TESTBENCH_CASE_FAIL`. Returning `TESTBENCH_CASE_RUNNING` continues execution with the next beat.

The terminal states have distinct meanings:

- `TESTBENCH_CASE_COMPLETE`: the case finished normally without issuing a PASS/FAIL verdict;
- `TESTBENCH_CASE_PASS`: the case finished and its assertions passed;
- `TESTBENCH_CASE_FAIL`: the case finished and at least one required check failed.

## 6. Environment Timing Contract

The per-beat order is fixed:

```text
before_dut(k) -> dut_run(k) -> after_dut(k) -> next beat
```

### 6.1 `before_dut`

Use `before_dut()` for work that must be visible to the current DUT execution:

- apply a delayed physical response caused by a previous DUT output;
- integrate a plant over the previous control period;
- generate sine waves, ramps, steps, faults, or scheduled state changes;
- prepare the current DUT inputs and feedback values;
- perform recording immediately before the current DUT execution;
- run the SFRA task and prepare the current injection sample.

### 6.2 `after_dut`

Use `after_dut()` for work that follows the current DUT output immediately:

- apply a zero-delay physical or logical environment effect;
- capture the current DUT input/output pair;
- record CSV data at a fixed decimation rate or when a value changes;
- update case-local result state;
- evaluate completion and assertions;
- close output files before returning PASS or FAIL.

### 6.3 `before_dut` and `after_dut` Usage Example

The following PI current-control case demonstrates how the two callbacks divide environment processing. The ideal `1/(sL)` plant uses the voltage calculated on beat `k` to produce the current observed on beat `k + 1`. `before_dut()` advances the plant and applies the time-based current-reference step:

```c
static void step_before_dut(double time_s)
{
    /* Apply voltage[k - 1] to the inductor before calculating beat k. */
    fixture.current_a +=
        (fixture.voltage_v / TEST_INDUCTANCE_H) * TEST_PERIOD_S;

    /* Present the updated plant state and current reference to the PI. */
    fixture.pi_feedback_a = fixture.current_a;
    if (time_s >= TEST_STEP_TIME_S)
    {
        fixture.current_ref_a = TEST_STEP_CURRENT_A;
    }
    else
    {
        fixture.current_ref_a = 0.0f;
    }
}

static TESTBENCH_CASE_STATE_E step_after_dut(double time_s)
{
    step_record(time_s); /* Records current[k] and the newly calculated voltage[k]. */

    /* Continue until the response satisfies the stability condition. */
    if (response_is_stable() == 0u)
    {
        return TESTBENCH_CASE_RUNNING;
    }
    /* Convert the final checks into the terminal test state. */
    return final_assertions_pass() == 1u
               ? TESTBENCH_CASE_PASS
               : TESTBENCH_CASE_FAIL;
}
```

The resulting CSV relationship is:

```text
current[k + 1] = current[k] + voltage[k] * Ts / L
```

In this case, `before_dut()` advances the environment and prepares the current DUT inputs, while `after_dut()` records the new DUT output and evaluates the test result.

## 7. Makefile Pattern

Keep the paths and source lists that normally change inside the `User modification section`. When creating a test project, edit this section and leave the common build rules unchanged.

```makefile
CC := gcc
CXX := g++

BUILD_DIR := build
TARGET := $(BUILD_DIR)/example_test.exe

# =================== User modification section begin ===================

# Project directories.
COMMON := ../common
CODE := ../../../code
LIB := $(CODE)/lib

# C source files.
C_SOURCES := example_test.c \
             $(LIB)/production_module.c

# C++ source files.
CXX_SOURCES := $(COMMON)/testbench.cpp

# Header search paths.
INCLUDE_DIRS := $(COMMON) \
                $(LIB)

# ==================== User modification section end ====================

CPPFLAGS := $(addprefix -I,$(INCLUDE_DIRS)) -DIS_TESTBENCH
CFLAGS := -std=c11
CXXFLAGS := -std=c++14
LDLIBS := -lm

C_OBJECTS := $(addprefix $(BUILD_DIR)/,$(notdir $(C_SOURCES:.c=.o)))
CXX_OBJECTS := $(addprefix $(BUILD_DIR)/,$(notdir $(CXX_SOURCES:.cpp=.o)))
OBJECTS := $(C_OBJECTS) $(CXX_OBJECTS)

vpath %.c $(sort $(dir $(C_SOURCES)))
vpath %.cpp $(sort $(dir $(CXX_SOURCES)))

.PHONY: all test prepare

all: prepare $(TARGET)

prepare: | $(BUILD_DIR)
	powershell.exe -NoProfile -Command \
		"Remove-Item -Path '$(BUILD_DIR)/*.o','$(BUILD_DIR)/*.exe' -Force -ErrorAction Ignore"

$(TARGET): $(OBJECTS)
	$(CXX) $(OBJECTS) $(LDLIBS) -o $@

$(BUILD_DIR)/%.o: %.c | $(BUILD_DIR)
	$(CC) $(CPPFLAGS) $(CFLAGS) -c $< -o $@

$(BUILD_DIR)/%.o: %.cpp | $(BUILD_DIR)
	$(CXX) $(CPPFLAGS) $(CXXFLAGS) -c $< -o $@

$(BUILD_DIR):
	mkdir $(BUILD_DIR)

test: prepare $(TARGET)
	$(TARGET)
```

The main user-modified values are:

- project paths such as `COMMON`, `CODE`, and `LIB`;
- C sources in `C_SOURCES`;
- C++ sources in `CXX_SOURCES`;
- header search paths in `INCLUDE_DIRS`.

`BUILD_DIR` selects the output directory, and `TARGET` selects the executable name. Before each build, `prepare` removes `.o` and `.exe` files while preserving existing CSV and log files. Source basenames must be unique because object filenames are derived from the basename.

## 8. Build and Run

From the repository root, compile one project without running it:

```powershell
mingw32-make -C platform/testbench/ac_loss_det
```

Build and run every case linked into that executable:

```powershell
mingw32-make -C platform/testbench/ac_loss_det test
mingw32-make -C platform/testbench/pi test
```

A successful executable prints a summary and returns process exit code 0:

```text
TESTBENCH SUMMARY | modules=1 cases=4 passed=4 completed=0 failed=0
```

Any failed case makes the executable return a nonzero exit code. Both the default build and the `test` target remove existing `.o` and `.exe` files before rebuilding. CSV and log files remain in `build/`.

## 9. CSV Recording

CSV ownership belongs to the individual case, not the common runner. A typical pattern is:

1. reset the fixture and open `build/<case>.csv` in `init`;
2. write the header immediately;
3. when beat 0 is needed, record `time_s = 0.0` in `dut_init()` after the DUT has been initialized;
4. record selected samples in `before_dut()` or `after_dut()` according to signal timing;
5. close the file in the terminal COMPLETE/PASS/FAIL path;
6. for asserted cases, make CSV open, write, or close failure contribute to the assertion result.

The first column of a time-domain waveform should be `time_s`. Recording does not have to occur every DUT execution. A case may record every N beats, on a value change, when a threshold is crossed, or when a frequency sweep completes one point.

## 10. AI Quick-Start Checklist

When creating a test project from this document:

1. inspect the DUT source, header, dependencies, initialization entry, and run entry;
2. inspect `platform/testbench/common/testbench.h` and create a test directory beside `common/`;
3. define a fixture containing the DUT, inputs, outputs, environment state, and recording state;
4. implement case `init`, module `dut_init`, module `dut_run`, case `before_dut`, and case `after_dut`;
5. register the DUT with `TESTBENCH_REGISTER` and each case with `TESTBENCH_CASE`;
6. copy the Makefile pattern, set `TARGET`, and modify the marked paths and source/include lists;
7. run `mingw32-make -C <test-project> test`;
8. inspect the summary and any generated CSV files.
