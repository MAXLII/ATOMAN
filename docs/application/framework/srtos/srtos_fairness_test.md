# 两个等耗时任务的实板计数测试

测试使用 GD32E507Z-EVAL、生产 SRTOS M 和生产 SVC/PendSV 端口。时间片为固定全局 1 ms，A、B 都以 `REG_TASK_MS(1u, ...)` 注册，调用同一个工作函数，各自在入口执行 `entries++`，返回前执行 `completed++`。恢复挂起现场不会重新累加入口计数。

启动时暂时屏蔽中断，使用 DWT 校准固定循环次数，使工作量约为 650 μs CPU 时间。任务执行固定次数的指令循环；被挂起期间的等待不计入循环工作量。A、B 使用相同循环次数。运行任务链表只保留 A、B，100 μs SysTick 提供必要时基。核心原有的空 Link 轮询注册项在测试初始化时从运行链表排除，调度实现不为本测试另加分支。

任务中的局部校验值跨越工作函数保存，用于检查恢复后是否仍属于原来的调用。观察通过 SWD 实时读取 RAM，采集期间不暂停 CPU；每组结束后暂停一次，取得一致的最终计数、现场池诊断及 CFSR/HFSR，再烧录下一组。首组 A 在运行链表前，第二组 B 在前，每组目标为 5 s；SWD 读取和终止快照使实际时间略长，结果记录实际 tick 时间。默认结束后恢复执行测试固件，只有显式传入 `--restore-demo` 才恢复示波器。

两个任务每毫秒合计需要约 1300 μs CPU，属于过载测试。目标是观察在当前规则下的实际分配，计数是否接近与程序是否正确保存/恢复现场分别记录。以两者平均计数为分母，差值不超过 1% 记作“计数接近”。

## 复现

在 base 根目录运行：

```powershell
./platform/gd32e507/tests/srtos_fairness/build.ps1 -Policy new_first
./platform/gd32e507/tests/srtos_fairness/build.ps1 -Policy fifo
python platform/gd32e507/tests/srtos_fairness/run.py --policy new_first --output build_fairness_new_first_results --seconds 5 --poll 2
python platform/gd32e507/tests/srtos_fairness/run.py --policy fifo --output build_fairness_fifo_results --seconds 5 --poll 2
```

需要独占开发板。测试通过 J-Link 69409716 烧录专用镜像并回读校验。测试源码在 `platform/gd32e507/tests/srtos_fairness/`。基线构建只在 `build_fairness_new_first/section.c` 中还原本次修改前的新任务优先策略，不向生产代码增加测试宏；固定窗口、周期更新、现场实现和负载保持一致。生成器检查关键替换次数，源码结构变化时终止构建。两版结果分别保存在上述 `--output` 目录，包含计数、校准值、ELF SHA256 和逐次 SWD 日志。

## 5 秒前后对照

2026-10-22 实板对照，偏差按 `abs(A-B) / ((A+B)/2)` 计算：

| 策略 | 顺序 | 实际时间 / s | A 入口计数 | B 入口计数 | 偏差 | 小于 1% |
| --- | --- | ---: | ---: | ---: | ---: | --- |
| 修改前：新任务优先 | A → B | 5.5218 | 5521 | 1717 | 105.112% | 否 |
| 修改前：新任务优先 | B → A | 5.5226 | 1717 | 5522 | 105.125% | 否 |
| 修改后：统一 FIFO | A → B | 5.5355 | 3766 | 3762 | 0.106% | 是 |
| 修改后：统一 FIFO | B → A | 5.5490 | 3774 | 3772 | 0.053% | 是 |

各组两个任务使用相同固定循环次数，启动校准均约 649.8 μs。四组局部现场校验错误、现场保存/释放失败、任务故障、CFSR、HFSR 均为 0。交换顺序后，旧策略偏向随顺序反转；统一 FIFO 两组均通过计数偏差判据，说明本次插队修复对这一等耗时场景有效，不代表不同负载下严格均分 CPU。

M/A9 生产调度函数的主机回归覆盖混合队列 FIFO、重复到期不重复入队、主动分步排尾、内联路径不得跳过挂起队首、窗口余量和 tick 回绕；PendSV 活动期间不重复挂起的回归也通过。A9 未进行实板验证。

本次短测结束时保留修改后的 B → A 双任务测试固件运行，未恢复示波器；之后按用户新要求恢复并验证了统一 FIFO 上的示波器固件，见[示波器设计 15.14](../../../design/debug/realtime_scope_design.md#1514-统一-fifo-后恢复示波器并复验)。旧的 300 s 结果仍保存在 `build_fairness_results/`，没有覆盖。

## 修改前的 300 秒历史结果

两组实板长测均已完成，最终计数取自 `result.json` 的各组 `final`：

| 运行链表顺序 | 实际运行时间 / s | A 入口计数 | B 入口计数 | 较多 / 较少 | 计数接近 |
| --- | ---: | ---: | ---: | ---: | --- |
| A → B | 300.5630 | 300563 | 93459 | 3.216 | 否 |
| B → A | 300.5545 | 93439 | 300554 | 3.217 | 否 |

两组启动校准分别为 649.811 μs 和 649.839 μs，同一组两个任务使用相同工作量。每个任务的完成计数均比入口计数少 1，对应结束快照时仍在执行或挂起的那次调用。局部值校验错误、现场保存/释放失败、任务故障、CFSR、HFSR 均为 0；这些结果只说明本次测试未观察到这些故障。

旧版调度规则优先执行新到期任务，再恢复挂起 FIFO。每个时间片中，链表前面的任务先完成约 650 μs 工作，另一个主要使用剩余时间；前面的任务通常不会进入挂起队列。因此挂起队列采用 FIFO 并不能保证两个任务均分执行次数。交换顺序后偏向反转，表明差异随运行顺序变化。总需求超过 CPU 容量解释了两者无法同时达到 1000 次/s，但不能据此把执行次数不均衡判为通过。

运行期 `min_wall_cycles` 出现 0，原因尚未核实，不作为耗时依据；上述 CPU 工作量依据启动时屏蔽中断校准后的固定循环次数。

这次历史长测只观察旧调度器，没有修改策略；当时结束后恢复了示波器演示固件，J-Link `verifybin` 回读校验成功。该历史镜像 ELF SHA256 为 `2B71F7B4BF3564CB9F31A7A8AB457AD3EA8B505638DB790F5E4A81C57BA591BA`，不是本次统一 FIFO 镜像。
